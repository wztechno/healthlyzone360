## Phase K1 — decisions local to the kitchen catalogue slices

| ID | Date | Decision | Detail / reference |
|---|---|---|---|
| D-054 | 2026-08-02 | The private Healthy360 kitchen workbook importer **reports and continues** on an unresolved raw-material designation, instead of failing loudly and abandoning the file | K1.8. This is a deliberate, single-scoped deviation from the programme's fail-loudly-abort default. §4.11 asks the importer for created / skipped / failed counts, and a count of failures only means something if a run survives one. So an unresolved designation costs its **own recipe line**, is reported by name with every sheet and row it appears on, and flags its sheet incomplete; the remaining lines and the other twenty-eight sheets import normally. It never fabricates an ingredient and it never silently skips a file. The alternative — one unknown spice discarding a whole correctly-read workbook — would have produced an operator fixing one dictionary entry per run for a fortnight |
| D-055 | 2026-08-02 | Designation resolution is **curated only**: a human-authored dictionary, then tenant ingredients, then the platform library. No fuzzy matching, edit distance, plural stripping or transliteration exists anywhere in the import path | K1.8; `app-modules/ingredients/database/data/kitchen-workbook-aliases.json`. No string metric separates "Cripsy Spice → Crispy Spice" (a typo) from "Sweet Paprika → Paprika" (a different product at a different price), and the failure mode of getting it wrong is a wrong allergen label rather than a wrong report. The dictionary also records the merges a curator **refused** (`never_merge`) and the product-to-recipe links a curator refused (`recipe_links_declined`), so a later reader sees a decision rather than an omission (risk R4) |
| D-056 | 2026-08-02 | A bare integer in a technical sheet's "Quantity Produced" cell is disambiguated by the sheet's **own cost-block wording**, and the ambiguity is reported every time | K1.8. Six sheets write a yield as a whole number with no unit. A fraction cannot be a piece count and `130 (7 kg)` states both, but `97` and `80` are genuinely ambiguous, and the sheets themselves disagree — sheet 11 claims a per-kilogram cost over a "yield" larger than its own input total. So the *transcription* consults the label once, emits `yield_shape_ambiguous` naming the sheet and the label that decided it, and everything downstream keeps the programme rule that a cost basis is derived from the version's yield fields and never from a label (appendix D findings #1/#2) |
| D-057 | 2026-08-02 | The sauce and dressing sheets import as **indicative recipes with no lines** — the "typical ingredients" prose is kept verbatim in `notes`, and only the declared allergen rows become data | K1.8. The source describes those columns as "typical Lebanese/Mediterranean formulations — validate against the kitchen's actual recipes before use". Splitting disclaimed prose on commas and calling the result a formulation would manufacture quantities nobody stated. The allergen columns are a real human statement — a class and the ingredient that triggers it — so they become `recipe_version_allergens` rows with `derivation = declared`, which a later recomputation may strengthen and may never weaken |
| D-058 | 2026-08-02 | The importer's **dry run executes the whole write path inside a transaction it always rolls back** | K1.8. Counting what would be created without doing it needs a second implementation of every insert-if-absent rule in the importer, and the day the two disagree is the day the dry run stops being worth running. Executing and rolling back makes "would create" mean exactly "did create, and then did not"; a test asserts row counts are identical either side of a dry run |
| D-059 | 2026-08-02 | The importer lives in the **Kitchens** module and that module's declared dependencies widen to the whole K1 family | K1.8. Catalogues could not host it: Pricing depends on Catalogues, so a Catalogues → Pricing edge would close a cycle the architecture test rejects. Nothing that may hold code depends on Kitchens, so widening it stays acyclic — and standing a kitchen up from its own workbook is what a kitchens module is for. `docs/architecture/module-registry.yaml` and `ModuleRegistryTest` change in the same commit as the code |

## Integration wave — decisions local to wiring the committed domains to HTTP

| ID | Date | Decision | Detail / reference |
|---|---|---|---|
| D-060 | 2026-08-02 | Domain exceptions declare their own wire shape through a `ProvidesApiError` interface in Support, rather than being mapped inside `ApiExceptionRenderer` | The domains (Verification, Customers, B2B) were built ahead of their HTTP surface and carry stable *reason strings* rather than wire codes, which was right — they did not own the vocabulary. Mapping those reasons in the renderer would have made Support import Verification, Customers and B2B, inverting the dependency every other module respects and making the one class every failure passes through depend on every domain that can fail. The interface keeps Support pointing only downwards, and a module that adds a refusal declares what it means on the wire in the same file. It is not a licence to build an error body: the return type is `ApiError`, so the code still comes from the shared enum and the correlation identifier is still added where it cannot be forgotten |
| D-061 | 2026-08-02 | The idempotency guarantee lives in **two** layers on purpose: `EnforceIdempotency` middleware and `OrderIdempotency` service | §4.14. Only the middleware can *replay* a response, because by the time a service returns the response is already gone; only the service holds for an order placed by a queued job or a console command, which never passes through a middleware at all. Neither subsumes the other, and the duplication is the smaller cost |
| D-062 | 2026-08-02 | `idempotency_keys.user_id` becomes nullable beside `customer_account_id`, with the unique key rebuilt over `COALESCE(user_id, customer_account_id)` | C1 shipped an honest hole — a guest had no user, so the service returned "unprotected" and let the order through with no guard. That was the wrong population to leave out: a guest checking out on a phone is exactly who double-taps. The coalesce is safe as a key expression only because a CHECK guarantees exactly one subject is set |
| D-063 | 2026-08-02 | `AgreementService::sign()` now **requires** a consumed `b2b_signatory` OTP challenge belonging to the signing user; `SigningEvidence::$otpVerified` can only be set by the service, never asserted by a caller | B1 recorded the challenge id unchecked and said so, because the verification module was being built in parallel. It is built. The column gains a real FK with `ON DELETE RESTRICT` — evidence a purge job can delete is not evidence — and the four failure modes (absent, wrong purpose, unconsumed, wrong subject) answer with one code and no detail about which, so a caller holding somebody else's challenge id learns only that it did not work. This is still **not** a qualified electronic signature (INT-007) |
| D-064 | 2026-08-02 | `OtpPurpose::isIssuable()` opens to all six purposes, and a new `grantsStepUp()` narrows which of them may stamp an `otp` step-up | The gate exists to stop a purpose being issued before the consumer that honours it exists. All six consumers now exist. The step-up replay risk the purpose column was built to prevent moves to `grantsStepUp()`, which admits only `closure_step_up` and `payment_details_step_up`: a contact-verification code must never unlock a payment change |
| D-065 | 2026-08-02 | `contact_points` gains `b2b_application_id` as a third owner kind rather than B2B growing its own contact table | §4.9, widening a named CHECK additively exactly as that clause anticipated. A B2B application names a signatory who may hold no account at all, and their destination still needs normalisation, hashing, verification state and a retire path. A separate table would have produced a second, subtly different implementation of all of it. The verified-value unique index is untouched and stays global across owner kinds, because "one proven holder of an address" is a statement about the address |
| D-066 | 2026-08-02 | `organisation_invitations` gets **no** row-level security policy, and the decision is recorded rather than deferred again | The management surface is organisation-scoped and could carry an `org-rls` policy, but the accept path resolves an invitation by *hashed token* before the acceptor is a member of anything — an org-match policy would break it, and a token-hash session variable would be a weaker mechanism than the token itself. Access is therefore service-mediated and token-gated. `RlsTest` pins the protected set, so this table's absence from it is a stated choice rather than an omission |
| D-067 | 2026-08-02 | `GET /reference/delivery-areas` makes `country_code` optional, reversing K1.7 | The original argument was right about *defaults* and wrong about *absence*. A client that has not asked for a country has not asked for the wrong one, and the consumer marketplace legitimately wants the whole gazetteer before it knows where the person is. `country_code` is embedded on every row, so an unfiltered page is unambiguous by construction. An unrecognised code is still a 400 |
| D-068 | 2026-08-02 | `allergens.severe_by_default` marks seven classes, and is documented as a **presentation default, never a diagnosis** | Closes the second M1 blocker. The set — crustaceans, egg, fish, peanut, tree nut, sesame, mollusc — matches the fixture the frontend was built against, which is the point: a default the two halves disagree about is worse than no default. The other seven are deliberately unmarked; coeliac disease and a milk allergy can both be extremely serious, what they are not is *reliably* so, and a default that cried wolf would train people to clear it without reading |
| D-069 | 2026-08-02 | The B2B signatory passcode goes to the **authenticated actor's own** contact point, and the application's named signatory address is recorded separately as an application-owned contact | The challenge must carry a subject `sign()` can match, and the only subject that means anything is the person in the session. So the named address is written down as evidence of who was nominated, and the person signing must independently hold it — if they do not, the refusal says the named signatory must sign in and sign for themselves, rather than letting an applicant step up on somebody else's behalf |
| D-070 | 2026-08-02 | `customer_accounts` RLS gains a third arm admitting **ownerless** rows, so the guest journey works at all | J1's policy admits a row belonging to the session's user or organisation. A guest account has neither — both NULL by CHECK — so it matched nothing, and the whole G1 surface would have answered `401 guest.session_invalid` in production while passing every Feature test, because those connect as the schema owner and bypass RLS by ownership. Found by reading the predicates. The rejected alternative was a fourth session variable: the account is discovered *by* validating the token and validating the token reads this table, so the variable cannot be set before the read it is meant to authorise — and the only way round that is publishing the token digest onto a shared database session, which is strictly worse than the token. The arm admits ownerless rows **only**; a registered customer's account still matches their session alone and a corporate account its organisation alone, and `RlsTest` pins both. What it concedes is that guests are isolated from each other in the application layer by their capability token rather than by a predicate — which is the strategy §4.12 names for them and exactly what `guest_sessions`, `carts` and `orders` already rely on, none of which carries a policy at all |

## Integration wave 2 — decisions local to subscriptions, closure and offboarding going live

| ID | Date | Decision | Detail / reference |
|---|---|---|---|
| D-071 | 2026-08-03 | The three tables the final backend wave gave read paths to — `subscriptions`, `account_closure_requests`, `b2b_offboardings`/`record_exports` — take **no** PostgreSQL policy, and the `RlsTest` pin stays at eleven | Decided per table rather than as one answer, and each reason is different. **`subscriptions`**: S1 declared `app-scope` on the C1 `carts`/`orders` precedent — a customer is a member of no organisation, so an org policy hides their own plan from them. A user-arm-via-account subquery would have served `/me/subscriptions`, and it would have made `GenerationService::tick()` read **zero rows** in every scheduler run: the hourly sweep is platform-wide by design, runs as `healthy360_app` with no context published, and would have failed *silently* — the tick would report `generated: 0` and nobody would notice until the food stopped. Making it work would mean rewriting a committed sweep to iterate organisations, to gain database isolation on a table whose sibling `orders` (which holds the delivery address) deliberately has none. **`account_closure_requests`**: a user-owner policy fits `/me/closure-requests/live` exactly and breaks `ProcessScheduledClosures` the same way — the safety net for a delayed job the queue lost is precisely the thing that must not depend on a session. **`b2b_offboardings`, `record_exports`**: B1 proposed `org-rls` and it is the wrong word. The only reader is a platform operator whose `X-Organisation-Id` is the *platform operator's* organisation while the row's `organisation_id` is the corporate customer's, so an org-match policy would hide every row from the one surface that reads it — the D-066 finding again. Their strategy is `platform-only`: no tenant read path exists, and both routes carry `platform.context` plus a platform permission. In all four cases isolation is the application layer, and every read names its scope — `SubscriptionLocator`, `ResolvesClosureRequest`, `ResolvesOffboarding`, and `ScheduleProjection::forOrganisation()` |
| D-072 | 2026-08-03 | `BlockerStatus` gains a fourth case, `advisory`, and `CreditMemoBlocker` is the first to return it | J2's `WalletBalanceBlocker::COVERS` explicitly declined to claim `credit_memos` — customer-held value S1 owns — and raised it for the integration wave rather than converting an open question into a false all-clear. The answer is a blocker over a new `CustomerCreditPresence` port, and it is **advisory rather than blocking**: a memo is a debt the *kitchen* owes the *customer*, so refusing the closure until it is settled would give the party that owes the money a veto over the erasure of the party owed it, and the slower a kitchen paid the longer it could keep somebody's data. It is also unnecessary — `credit_memos.customer_account_id` points at a row closure anonymises rather than deletes, so the obligation and its currency survive intact and stay settleable. `advisory` is a genuine fourth state: `clear` is the absence of a finding and carries no count, `not_applicable` means nothing was checked, and `blocking` would be wrong on the merits. `stopsClosure()` returns false for it; the count reaches the closure screen and the audit trail.
