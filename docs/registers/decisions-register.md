## Cross-phase architecture decisions (Order-Kitchen programme, phase P0)

D-036 to D-053 are the §4 decisions of the Order-Kitchen master plan v2, frozen before any domain migration exists and binding on every phase of that programme. They renumber the provisional D-036+ identifiers that the three design reports proposed independently. Decisions local to a single phase — guest token design, MSA click-wrap, tombstone policy and the like — are recorded by the phase that makes them, not here.

| ID | Date | Decision | Detail / reference |
|---|---|---|---|
| D-036 | 2026-08-02 | Module status vocabulary is `planned` / `foundation` / `active` / `deprecated` / `retired`; the eleven platform modules become `active` | master plan v2 §4.1; `docs/architecture/module-registry.yaml`, enforced by `apps/api/app-modules/support/tests/ModuleRegistryTest.php`. A status change and the architecture test that enforces it land in the same commit, always |
| D-037 | 2026-08-02 | Recipe outputs are modelled by `recipe_version_outputs` (version-specific yields, several outputs, one primary); `ingredients.produced_by_recipe_id` is dropped from the design | master plan v2 §4.2; an intermediate is simply an ingredient that appears in some version's outputs — this removes the circular FK migration and the fabricated stub-recipe special case |
| D-038 | 2026-08-02 | Plan durations use `duration_kind` (`one_off` or `fixed_days`) with a nullable `duration_days` and a CHECK, not a zero-day sentinel row | master plan v2 §4.3; widens the `PlanDurationOption` wire contract (supersedes design-report OD-3) |
| D-039 | 2026-08-02 | Two monetary representations: commercial prices are `amount_minor bigint` plus `currency_code`; calculated recipe costs are `decimal(18,6)` in **major** currency units plus `currency_code`. Every value carries exactly one currency; no cross-currency arithmetic and no summing cost columns into price columns | master plan v2 §4.4; extends D-030. "Decimal minor units" is never used as a description. Both prohibitions are architecture-tested from K1.3 |
| D-040 | 2026-08-02 | `measurement_units` gains a `dimension` (mass, volume, count, serving, package); automatic conversion happens only within a dimension, and pack equivalences (bottle or gallon content) are product data on catalogue-item pack variants | master plan v2 §4.5 |
| D-041 | 2026-08-02 | Allergen governance: canonical codes are immutable regulatory identities (code primary key, deactivate only — never rename or delete); the platform owns display names, Arabic, market applicability, thresholds and notes; kitchens own mappings, containment, verification source and review requests | master plan v2 §4.6; the fourteen EU-14 codes match the frontend `AllergenCode` union one-for-one |
| D-042 | 2026-08-02 | Publication lifecycle for sellable and publishable records is `draft`, `review_required`, `published`, `retired`; publication is an explicit action gated by a computed readiness evaluator; critical allergen conflicts quarantine the record as `review_required` and block publication structurally; published recipe versions are immutable and changes are new draft versions | master plan v2 §4.7; "publishable" is the evaluator's verdict, never a stored state. Operational records keep the separate `active`/`inactive`/`archived` family |
| D-043 | 2026-08-02 | Every anonymous or customer endpoint serialises through an explicit PublicProjection presenter, against a named denylist: recipe lines, raw-material quantities, unit costs, cost snapshots, waste coefficients, supplier identities, margins, data-quality notes, document paths, KYC, signature evidence, review commentary and internal recipe ids the consumer contract hides | master plan v2 §4.8; automated literal and key-denylist sweeps run across the whole anonymous surface in every phase that adds a public endpoint |
| D-044 | 2026-08-02 | Sensitive entities take explicit nullable owner foreign keys plus an exactly-one CHECK — never `owner_type`/`owner_id`. A phase that adds an owner kind widens the CHECK additively | master plan v2 §4.9; applies to `contact_points`, `otp_challenges` and uploaded documents |
| D-045 | 2026-08-02 | `users.email` stays the canonical authentication identity; `contact_points` own notification destinations and verification state. One write path mirrors the login email and a drift test pins the two together | master plan v2 §4.10; Fortify is unchanged. Login by phone would be an identity migration and is out of scope |
| D-046 | 2026-08-02 | Exactly three data-loading mechanisms: committed platform reference seeders, committed synthetic fixtures (no real formulations or costs), and a private GreenLife importer reading an out-of-repo source path. Confidential source data is never committed to the repository | master plan v2 §4.11; `php artisan kitchen:import-greenlife --source=<private path>` — manifest and sha256 checksums, dry-run, counts, unresolved-alias, data-quality, allergen-review and quarantine reports, insert-if-absent so operator edits are never overwritten, idempotent, environment-allowlisted, audited. Supersedes the committed technical-sheet fixtures of plan v1 |
| D-047 | 2026-08-02 | Every table names exactly one isolation strategy from a fixed vocabulary of seven: `platform-public-ref`, `org-rls`, owner-RLS (`user-owner-rls` / `customer-owner-rls`), `join-rls-parent`, `platform-only`, `capability-token`, `append-only-ledger`. "Application scoped" is not an isolation strategy | master plan v2 §4.12; extends ADR-0007. | D-048 | 2026-08-02 | Optimistic locking: management single-resource GETs return `ETag: "<lock_version>"`, writes on lock-versioned resources require `If-Match`, a missing precondition answers HTTP 428 and a stale one answers the existing 409 `resource.conflict` | master plan v2 §4.13; `docs/api/conventions.md`.
