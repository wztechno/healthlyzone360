# Assumptions Register

Provisional working assumptions, labelled honestly as such (per the source instruction document §4). Each must be validated or converted into a confirmed decision; none is a confirmed fact.

| ID | Assumption | Basis | Impact if wrong | Validation route |
|---|---|---|---|---|
| A-001 | MENA-first demand: the nine launch markets provide sufficient early demand for the clinic + kitchen combination, with GCC markets driving paid usage and Lebanon/Jordan/Egypt driving volume | Founder market knowledge; not yet validated by research | Launch-market prioritisation, pricing and Arabic-first effort misallocated | Discovery/validation work in product Phase 1 (source doc §11) |
| A-002 | Gulf users expect **Latin digits** for clinical and financial numerals even in Arabic UI | Common regional convention in medical/banking software; not user-tested | Numeral rendering wrong for key audiences; trust damage in clinical contexts | Recorded as configurable default pending management decision (OQ-001); usability testing in Arabic locales |
| A-003 | Demo/seed data (organisations, branches, memberships, roles) is fictional and clearly labelled; no real clinic or patient data enters the system before consent, audit and RLS phases pass their gates | Team practice | Accidental processing of real personal/health data without controls | Seeder review; environment policy in `docs/security/` when authored |
| A-004 | PHP 8.4 will be available on the eventual production host | Docker-based deployment assumed (Plan §22) | Pest 5/Laravel 13 baseline unusable on host; forced re-platforming (ADR-0008) | Confirm when hosting decision is made |
| A-005 | Developers run Docker Desktop (or equivalent) on Windows/macOS/Linux; the bare Windows host's missing `pdo_sqlite`/`intl` extensions are not blockers because PostgreSQL-backed tests and the Docker toolchain are canonical | Plan §22; host inspection 2026-07-30 | Local onboarding friction; intl-dependent code fails on bare host | Clean-clone setup validation (Phase 2 gate) |
| A-006 | No launch market currently imposes data-residency requirements that prohibit a single shared regional database for the foundation phase | Not yet legally assessed — assumption, not advice | Per-country database placement rework (ADR-0002) | Per-country regulatory assessment (OQ-003) before onboarding real tenants in each market |
| A-007 | Foundation-phase audit-log volume is modest (thousands of rows/day, not millions), so partitioning can be safely deferred | Pre-launch usage expectations | Painful retrofit of partitioning/retention on a large hot table (R-007) | Volume review at first production tenant; retention decision OQ-002 |
| A-008 | **REVISED 2026-08-02.** Superseded text: *"Email is a sufficient verification and recovery channel at launch; SMS/WhatsApp OTP is not required for the foundation."* The journeys source requires SMS and WhatsApp OTP, so the assumption no longer holds. Replacement: the OTP framework is channel-agnostic from J1 with a real email driver, while SMS and WhatsApp ship behind driver interfaces with log/fake drivers outside production, and **production phone verification stays disabled until a real provider is selected and approved** | Plan §13 scope, corrected by the Order-Kitchen journeys source (master plan v2 §3 #16, appendix A) | A phone-required activation rule shipped on a fake SMS driver would fail every activation in production; email-only activation is therefore the production default | Provider selection OQ-008 / INT-005; deliverability gate A-011; revisit at first real-tenant onboarding |
| A-009 | The Expo SDK 57 / RN 0.86 pairing remains supported long enough to complete Phases 5–7 without a forced mid-foundation SDK upgrade | Expo release cadence | Mid-phase upgrade churn across navigation, reanimated, nativewind | Watch Expo SDK 58 timeline; ADR-0009 review trigger |
| A-010 | Starter-kit Teams feature can be removed without destabilising Fortify authentication flows | Phase 0 code inspection pending | Auth regressions during Teams removal (R-009) | Identify Teams/Fortify coupling before removal (Plan §5) |
| A-011 | SMS deliverability and per-message cost are acceptable across all nine launch markets at transactional OTP volumes, including the resend and channel-fallback behaviour the journeys source specifies | Not measured; no provider selected (OQ-008, INT-005); regional delivery rates and sender-ID registration rules vary sharply between Lebanon, the GCC, Jordan and Egypt | Phone-required activation is unreachable or uneconomic in some markets, stranding onboarding at the OTP step; the channel-fallback design becomes decorative | **Validate before enabling phone-required activation** — phone verification stays configurable and off in production until deliverability and unit cost are measured per market (master plan v2 §3 #16, A-008 revision) |
| A-012 | "Patient" is a D2C-shaped customer account linked to a clinic, not a separate identity model — clinical intake is deferred and no patient-specific identity is built before it | The source journeys document has no Patient journey section; provisional reading recorded rather than invented (master plan v2 §2.5) | Clinical intake rework: patient identity, practitioner relationships, clinical consent, special-category processing and retention all change shape if a patient is not a customer | **Expires at phase CL1 discovery**, which decides patient identity explicitly; jurisdiction assessment OQ-003 |
