# 04 — Data and API Architecture

> Status: Phase 1 architecture baseline. Migrations are Planned — Phase 3; the API surface is Planned — Phase 4. Wire-level detail (envelope field semantics, header validation rules, error-code catalogue) lives in `docs/api/conventions.md` and is not duplicated here.

## Identifier strategy

- **Problem.** Mixing identifier schemes ad hoc (auto-increments here, database UUIDs there, application UUIDs elsewhere) makes data movement, merging and auditing across a multi-tenant platform error-prone.
- **Recommendation.** Use **UUIDv7 consistently**, generated by the application through a central Healthy360 identifier service (Support module). ISO codes remain the primary identifiers for stable reference data where appropriate (e.g. countries, currencies, languages). PostgreSQL-native UUIDv7 may be used for database-only records where justified. Do **not** mix application-generated and database-generated primary keys arbitrarily.
- **Benefit.** Time-ordered, index-friendly, globally unique identifiers that the application controls; human-stable ISO keys where the standard already provides them.
- **Implementation impact.** One identifier service in Support; model base classes use it; any exception (database-generated) must be justified per table.
- **Risk of omission.** Arbitrary mixing produces inconsistent join/index behaviour and ambiguity about where identity is minted.
- **MVP status.** Adopted; identifier service Planned — Phase 3.

## Standard column conventions

| Convention | Rule |
| --- | --- |
| Primary key | Application-generated UUIDv7 (`id`); ISO code PKs for stable reference data |
| Tenant scoping | `organisation_id` on organisation-owned rows; `branch_id` where branch-scoped |
| Provenance | `created_by` where the creating actor matters |
| Timestamps | `created_at` / `updated_at` throughout |
| Concurrency | `lock_version` only on resources supporting optimistic concurrency (paired with `If-Match`) — not added speculatively |

## API principles

All implemented endpoints live under `/api/v1` and are described spec-first in OpenAPI 3.1.

### Response envelopes

- Success: `{ "data": { … }, "meta": { … } }`
- Error: `{ "error": { "code", "message", "details", "correlation_id" } }`
- Documented exceptions to the envelope: empty `204` responses, file downloads, streaming responses, health checks.
- Step-up authentication is signalled as **HTTP 403** with `error.code = auth.step_up_required` (not 423).

### Headers

| Direction | Header | Purpose |
| --- | --- | --- |
| Client → server | `X-Organisation-Id` | Intended organisation context (server-validated, never trusted) |
| | `X-Branch-Id` | Intended branch context (server-validated) |
| | `Accept-Language` | Locale negotiation (en / ar) |
| | `X-Client-Request-Id` | Client-generated request identifier |
| | `X-App-Mode` | Build family (`customer`, `staff`, `kiosk`, `driver`, `all-dev`) |
| | `X-Client-Version` | Client build version |
| | `X-Client-Platform` | web / ios / android |
| Server → client | `X-Correlation-Id` | Server-generated correlation identifier, echoed in error envelopes |

**`Idempotency-Key`** is used only on explicitly idempotent command endpoints; clients must not attach a new idempotency key automatically to every mutation. **`If-Match`** is used only on resources that support optimistic concurrency.

## OpenAPI tooling and the generated client

- **Problem.** A hand-written TypeScript client drifts from the API; multiple ad-hoc clients drift from each other.
- **Recommendation.** OpenAPI 3.1 is the contract for implemented endpoints, linted and bundled with **Redocly**. Exactly **one** generated TypeScript client, produced by `@hey-api/openapi-ts` behind a **project-owned generation script** (pre-1.0 tools are always wrapped), with generated-file **drift detection** in CI. Generated code may be imported **only through the API repository layer** — never directly by screens or hooks.
- **Benefit.** The spec is the single source of truth; the client cannot silently diverge; the generator can be swapped without touching consumers.
- **Implementation impact.** Contract tests for implemented endpoints; fixtures validated against generated schemas; backend CI runs OpenAPI lint and bundle.
- **Risk of omission.** Contract drift surfaces as runtime failures on native builds, where redeployment is slow.
- **MVP status.** Planned — Phase 4 (spec + client generation); drift detection in Phase 7 CI. Recorded as ADR-005.

**Runtime request/response validation:** do **not** build a custom schema-validation fallback in Phase 1. A short validator spike selects one maintained PHP validation path; if none proves reliable, the phase ships with OpenAPI linting + generated-client compilation + targeted contract assertions + endpoint smoke tests, and full runtime schema validation is recorded honestly as deferred.
