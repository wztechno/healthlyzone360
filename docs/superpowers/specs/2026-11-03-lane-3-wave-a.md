# Lane 3: P1 Wave A, the real team can use it

Date: 3 November 2026. Branch P0-Stage1. Migrations `2026_11_03_03xxxx`.

## Built

1. **Roles for real jobs.** Templates are the owner's jobs, each with a plain description in both languages. Owner, Manager (`kitchen_manager`), Finance, Cashier (`order_desk_agent`), Chef, Cook (`kitchen_staff`), Storekeeper or buyer (`procurement_manager`), and a new Driver (`kitchen_driver`). The platform role reads Platform super admin. Branch Manager now opens the kitchen display.
2. **Admin phone header.** Below `md`, Workspaces and Sign out are icon buttons, in `AreaShell`.
3. **Arabic allergen labels.** The kitchen display, the order lines, the plan-day badges and the ingredient and recipe lists read `allergenLabel` (`marketplace:allergens.*`) instead of the raw code.
4. **Ingredient copies.** Opening a library row writes nothing; a copy is the "Save a copy for this kitchen" button. Packaging shares the screen. A copy no longer gets its own shelf while its original has one, in either direction. `kitchen:merge-duplicate-stock` is read-only unless `--apply`. `/kitchen/stock-duplicates` lists what needs a person. Archiving an ingredient deletes a shelf nothing has touched.
5. **Holidays and branches.** `branch_closures` holds date ranges. `BranchScheduleLookup::explain` answers `closed` inside one, and the waiting-time clock stops. `POST /kitchen/branches` and a New branch dialog on `/kitchen/branch-operating`.
6. **Setup and go-live.** `/kitchen/setup`, in the wholesale checklist's shape, with a hub Callout. A new kitchen starts `not_open_yet`; customers get `kitchen_not_open`, the desk gets a warning.
7. **Platform "no owner".** Fixed; the cause was not only the role split, see below.

## What changes for existing role holders

Migration `2026_11_03_030001` only adds. No grant is removed, no assignment moves, no role is deleted. It reaches templates and copies with an empty `created_by`, in the style of `grant_order_supervise_permission`. A role a kitchen created keeps exactly what it has. A copy whose grants a kitchen edited by hand still gains these codes, because the two cannot be told apart.

| Holder | Gains |
|---|---|
| Owner, administrator, kitchen manager | `order.prepare_organisation` |
| Chef, cook | `order.prepare_organisation`: the wall with Start and Ready. No order book, no prices, no street address on it |
| Branch manager | `order.prepare`, `order.view`, `order.manage`, `order.supervise`, `order.view_customer_contact`, `order.create_on_behalf`, `customer.create_on_behalf`, `catalogue.view`, `inventory.view`, `production.view`, `organisation.view_current`. They also start receiving staff alerts |
| Everyone else | Nothing |

Names change only where a copy still carries the old template name. Descriptions land only where there is none. `reference_editor` renames the same way.

## Decisions

- **`order.prepare_organisation`, a new code.** Start and Ready sat on `order.manage_organisation`, which also cancels and takes cash. Giving that to a cook was wrong, and `order.view_organisation` would have shown cooks every total, which the registry promises they never see. So the wall has its own code and `permission:a,b` now passes on either.
- **Money on the wall.** A holder of only that code gets the same ticket with money zeroed and the street address nulled. One contract, two audiences.
- **Hidden, not deleted.** `organisation_admin`, `branch_manager`, `member` and `commercial_manager` leave the role list only while nobody holds them and no administrator made or changed them. Computed in code, so no migration touches a row and a held role can never vanish. The row still resolves by id.
- **Manager is `kitchen_manager`.** `branch_manager` is fixed for whoever holds it and hidden otherwise. One manager on the picker matches the owner's list. Restoring it is removing one word from `RETIRED_TEMPLATE_CODES`.
- **Owner, not Kitchen owner.** The template is copied into corporate customers too, and "Kitchen owner" would be wrong on those.
- **Driver grants no order code.** The run sheet narrows by `driver_user_id`, and any active member can still be handed a delivery.
- **Merge rule.** Automatic only for a copy and its original, same unit, at most one with movements, no open work on the row that goes. Everything else is listed with a reason. **Two shelves that both have movements stay on the list**: the ledger is append-only and cascades with its shelf, so dropping either erases history. `resolveStockItem` keeps both working, and now also reads from a library row to its copy.
- **The review list is computed, not stored**, so it cannot go stale. It is read-only.
- **Closures.** Ranges, not day rows. Reads stay open like `branch_opening_hours`, because carts read the schedule with no organisation declared; writes carry the organisation policy. `kitchen_closed` was not reused: the existing `closed` answer already means this.
- **Go-live.** Owner only (`organisation.update_current`). `not_open_yet` defaults false, so every existing kitchen stays open. Hours, delivery, menu and prices are required; team is not. There is no way back to not open: a kitchen that must stop has the pause and closures.
- **New branch** is refused to a membership bound to one branch, and takes the kitchen's country and timezone.

## The "no owner" cause

`withoutTenancy()` lifts the Eloquent scope and leaves row-level security. Under the operator's session the `roles` policy shows templates only and the `organisation_memberships` policy shows the operator's own rows. So since `2026_10_26_000001` gave every kitchen its own roles, every kitchen read as ownerless. Pest runs as the migrator and bypasses RLS, which is why nothing failed. The `_standard` split was real but secondary; it is covered too. Fixed by reading each kitchen's owners inside `DatabaseTenantContext::during()`. `KitchenOwners::revoke` had the same blind spot and is fixed the same way.

## Skipped

- **PIN and idle lock (item 8).** Not built. It swaps who a request runs as, so it is a new sign-in factor: device enrolment, short-lived per-person tokens, hashed PINs with limits per person and device, and changes to the session machine on web and native. None of it can be exercised here tonight (no tests, no Metro), and shipping untested identity code is the failure the brief warned against. Suggested shape: a manager enrols a tablet; a PIN exchanges for a short token for that real user with their own permissions; idle discards the token client-side and it expires server-side.
- **Actions on the review list.** No Merge or Keep both button. Add one if rows linger; both-with-history needs a ledger decision first.
- **Marketplace.** A not-open kitchen is refused at checkout and preview, but its listing is not hidden. It has nothing published until late in setup.
- **Closure dates in the customer date picker.** The date is refused on selection, not greyed out.
- **Header test.** No Jest test for the phone width; the existing shell tests cover the buttons by testID.
